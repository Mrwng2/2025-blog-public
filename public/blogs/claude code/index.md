# CLAUDE.md

为了减少常见的 LLM 编码错误，可以制定一些行为准则。根据需要将这些准则与特定项目的操作指南相结合。

权衡：这些指导原则更倾向于提倡谨慎行事，而非追求速度。对于简单的任务，还是应该依靠自己的判断来行事。

## 在编写代码之前先思考一下。


**不要妄下判断。不要隐藏自己的困惑。要坦然面对各种权衡。**

在实施之前：

- 请明确说明你的假设。如果不确定，就直接提问吧。
- 如果存在多种解释，那就把它们都提出来——不要独自决定。
- 如果存在更简单的解决方案，那就请说出来吧。在合适的时候提出反对意见吧。
- 如果有什么不清楚的地方，就停下来。指出那些令人困惑的内容。提问吧。

## 2. 先追求简单性

**解决该问题所需的最少代码量。没有任何推测性的代码。**

- 除了所要求的功能之外，没有其他特色了。
- 对于一次性使用的代码，无需进行抽象处理。
- 没有任何“灵活性”或“可配置性”是未被要求的。
- 对于无法处理的情况，没有错误处理机制。
- 如果你写了 200 行代码，但实际上只有 50 行内容，那么请重新编写这部分代码。

问问自己：“一位资深工程师会不会认为这种表述过于复杂了呢？”如果答案是肯定的，那就简化一下吧。

## 3. 手术干预

**只接触那些你必须接触的事物。只清理属于你自己的混乱局面。**

在编辑现有代码时：

- 不要试图“改进”相邻的代码、注释或格式。
- 不要对已经没有问题的代码进行重构。
- 与现有风格相融合，即使你希望以不同的方式来实现。
- 如果你注意到有无关的代码被删除了，请务必提出来——不要直接删除那些代码。

当你的修改导致了一些文件变得“孤儿”状态时：

- 删除那些由于你的修改而变得不再需要的导入语句、变量和函数。
- 除非有要求，否则不要删除已有的无用代码。

测试要求：所有被修改的行都必须直接指向用户的请求。

## 4. 以目标为导向的执行方式

**明确成功的标准。不断重复这一过程，直到确认达到标准为止。**

将任务转化为可验证的目标：

- “添加验证” → “为无效输入编写测试，确保它们能够通过验证”
- “修复这个漏洞” → “编写能够重现该漏洞的测试案例，然后确保测试通过”
- “重构 X” → “在重构前后确保测试通过”

对于需要多步完成的任务，请简要说明计划：

```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

明确的成功标准能让你独立地循环执行任务。而模糊的标准（比如“能运行就行”）则需要通过不断的沟通来明确其含义。

---

这些指导方针在以下情况下能够发挥作用：对差异化的修改减少，因过度复杂化而导致的重写次数减少，以及将问题的澄清放在实施之前而不是之后。.
